### 为什么这 2 个组合没测

opencode 环境只能访问 docker API on `http://172.16.0.40:2375`。在该环境跑 Linux SMB server 受限于:

| 限制 | 实际表现 |
|:---|:---|
| `docker pull` 新镜像 | ❌ 内部防火墙/镜像仓库不可达 (尝试过 alpine/python/eclipse-temurin 都失败) |
| `tokio::spawn` 多线程 | ❌ 默认 seccomp 策略拒绝线程创建 (`Operation not permitted (os error 1`) |
| `SecurityOpt: seccomp=unconfined` | ✅ 验证可解决多线程问题 |
| `apk add openjdk21` | ⚠️ 包下载慢且偶发失败 (apk 仓库限速) |
| Linux server binary + Java FFM | ❌ 需要预装 Java 的镜像 + 加载 .so |
| `ARG_MAX = 128KB` | ⚠️ 单个 env 变量受限, 需要分多个 env 或 docker archive API |
| Rust build 一次成功, 后续 reset 丢失了镜像 | ❌ 无法重新 build (上面限制叠加) |

**已验证 workaround**: 在容器启动时传 `SecurityOpt: ["seccomp=unconfined","apparmor=unconfined"]` 可解决多线程问题。但后续 `apk add openjdk21` 慢/失败 + `ARG_MAX` 限制 + `rust build` 重置 = 无法在本环境完整跑通 Linux SMB server 测试。

**风险评估**: 协议层是 OS 无关的。Linux→Windows 完整端到端 (NEGOTIATE / SESSION_SETUP / TREE_CONNECT / QUERY_DIRECTORY) 已验证。Linux server path 与 Windows server path 唯一区别是 native library 加载方式 (Linux .so 通过 ELF loader, Windows .dll 通过 PE loader), 不影响 SMB 协议行为。

**如果实际生产需要 Linux server**, 需要在 Linux 物理机/VM 上 build + run (Docker 环境外的工作)。

## 代码修复（关键变更）

### 1. Rust server 端支持匿名访问 + 接受 smbj 的 empty security buffer

修改 `local-smb/src/lib.rs`:
```rust
if user_clone.is_empty() {
    // Empty user means anonymous access is intended.
    share = share.public();
} else {
    share = share.user(&user_clone, Access::ReadWrite);
}
```

### 2. Rust server 端 NTLM anonymous fast path

修改 `local-smb/src/proto/auth/ntlm.rs`:
```rust
if auth.user.is_empty() {
    return Ok(AuthOutcome {
        identity: Identity::Anonymous,
        session_key: [0u8; 16],
    });
}
```

### 3. Rust server 端 ENCRYPTION context (修复 smbj-0.14 NPE)

修改 `local-smb/src/handlers/negotiate.rs`:
- smbj-0.14.0 不识别 TYPE_SIGNING (0x0008)，enum 里只有 0x0001/0x0002/0x0004/0x0005
- 把 SIGNING 改成 ENCRYPTION (0x0002)，smbj 正常解析
- smbj 客户端启用 AES-128-GCM 加密路径

### 4. Rust server 端接受 SMB 空 security buffer

修改 `local-smb/src/handlers/session_setup.rs`:
```rust
let blob = req.security_buffer;
if blob.is_empty() {
    // smbj 0.14 sends SESSION_SETUP with empty security buffer
    // during first round of authentication.
    tracing::debug!("first round with empty blob; treating as NEGOTIATE");
}
```

### 5. 客户端 SmbClient.java 支持匿名

修改 `SmbClient.java`:
- `parseUri()` 在 userPass 为空时 user 设为 `null`（而非默认 "guest"）
- `login()` 在 user 为 null/empty 时用 `AuthenticationContext.anonymous()`

### 6. SmbClientExample 支持运行时长

修改 `SmbServerExample.java`:
```java
long duration = Long.parseLong(System.getProperty("smb.duration", "2000"));
...
Thread.sleep(duration);
```

## 当前已知问题清单（按优先级）

### 🔴 优先级高

无。

### 🟡 优先级中

1. **Linux server 这条部署形态未实测**
   - 问题：Docker API 在 172.16.0.40 严格限制：
     - 不允许 pull 新镜像
     - 容器默认 seccomp 拒绝多线程（`Operation not permitted`）
     - `apk add openjdk21` 慢/失败
     - ARG_MAX 限制单 env 变量 < 128KB
   - 影响：4 种组合中的 2 种（Linux↔Linux、Linux server↔Windows）未实测
   - 已验证 workaround：容器加 `SecurityOpt: ["seccomp=unconfined","apparmor=unconfined"]` 可解决多线程
   - 后续修复：直接在 Linux 物理机/VM 跑 server binary（需要 root + 允许多线程）

2. **示例工程未走 CI / 自动测试**
   - 现状：所有测试是手动跑命令行
   - 修复方法：加 GitHub Actions 工作流自动跑端到端测试

### 🟢 优先级低（不影响功能）

3. **macOS dylib 是 16 字节占位**
   - 现状：未在 macOS 上实测
   - 影响：macOS 用户跑示例会失败
   - 修复：在 macOS 主机重新 cargo build --target aarch64-apple-darwin

4. **NTLM user+password 认证未实测**
   - 现状：只验证了 anonymous (空 user) 认证路径
   - 影响：需要密码访问的 share 没法测
   - 修复：debug smb-server 的 NTLM 校验实现

5. **smbj-0.14 不识别 SIGNING context (0x0008)**
   - 现状：smbj 已归档，0.14.0 是最后稳定版
   - 影响：被迫用 ENCRYPTION context (smbj 启用 AES-128-GCM 加密)
   - 修复：换 fork（smbj-extended / enterprise-msal），需重写 SmbClient.java

## 最终结论
- ✅ **完整端到端工作**：NEGOTIATE → SESSION_SETUP 匿名 → TREE_CONNECT → listFiles 返回 1 项带文件大小/时间戳
- ✅ **跨平台**：Linux 容器 → Windows SMB server TCP + 完整 SMB 协议均通过
- ✅ **当前 smbj-0.14.0 + Rust SMB server 方案完整可用**，无需更换 SDK
- ⚠️ **真实风险点**：Linux server 这条部署路径**未实测**，间接通过协议层对称性论证（合理但不严格）
- ⚠️ **user+password 认证**未实测 — anonymous 路径 OK，密码路径可能有问题
